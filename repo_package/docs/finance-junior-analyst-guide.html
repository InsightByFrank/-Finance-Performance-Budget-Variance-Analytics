Foundations

Understanding the Dataset

What's actually in this workbook, before touching a single chart or formula.

This workbook is a small company's general ledger, spread across four sheets. Here's what each one is actually telling you:

TRANSACTION (1,389 rows)

Every real money-in or money-out event from Jan 2022 to Dec 2024 — an invoice sent, a bill paid, a deposit received. One row = one transaction. This is what actually happened.

BUDGET (1,229 rows)

One row per account, per department, per month — the amount that was planned to be spent or earned. This is what was supposed to happen.

ACCOUNTS (35 rows)

The chart of accounts — every account name (like "SaaS Revenue" or "Salary & Wages"), grouped into categories (Income, Cost of Goods Sold, Operating Expenses).

DICTIONARY

A plain-English definition of every column in the other three sheets — your first stop whenever a column name is unclear.

The One Idea That Unlocks Everything Else TRANSACTION and BUDGET are answering two different questions about the same business — "what happened" vs. "what we planned." Keeping them as two separate tables, both pointing back to the same Accounts and Departments, is what makes it possible to ask "how far off were we?" later. That single decision shapes the entire model and every formula in this guide.

A Few Things Worth Knowing Before You Build Anything

  • Every transaction already has a clean, unique ID — no work needed to create one.
  • The ACCOUNT column and the COD_ACCOUNT column say the same thing two ways — one is the code (e.g. 40100), the other is the code plus a label (e.g. "40100 SaaS Revenue"). Use the code as your reliable key; clean up the label for anything a person will read.
  • Look closely at the vendor names and you'll spot "LinkedIn" and "LinkedIn Ads" — almost certainly the same vendor, typed two different ways. Real datasets do this constantly; it's worth catching before you build anything that counts by vendor name.
Data Model

The Data Model, Simply

Two fact tables, five small dimension tables, one date table.

Instead of one flat sheet, the model separates what happened (numbers you add up) from what describes it (things you filter or group by):

Why This Matters for the Dashboards Because Fact_Transactions and Fact_Budget both connect to the same Dim_Account, Dim_Class, and Dim_RevenueExpenses tables, you can filter both fact tables at once — pick "Sales & Marketing" in a slicer, and both the actual spend and the budgeted spend for Sales & Marketing update together. That's what makes every Budget-vs-Actual formula in the next section work with a plain subtraction instead of a complicated join.
Worth Knowing — the "Department" Slicer's Real Source In the finished report, the Department slicer on both pages is built directly on Fact_Budget[CLASS] rather than Dim_Class. It still works — Power BI filters through the relationship either way — but it's a useful reminder that a slicer doesn't have to point at a dimension table to function; it just has to point at some column that's connected to the tables you want filtered. If a chart ever doesn't respond to a slicer the way you expect, checking exactly which table and column that slicer is built on is the first thing to look at.
DAX

The Complete DAX Reference

Every measure needed to power both dashboards — base numbers, month-over-month comparisons, and the sparkline behind every single KPI card.

1. Build the Date Table First

Nothing with a "vs prior period" comparison or a sparkline will work correctly without a proper date table, marked as the model's official date table. Build this before any other measure:

DAX — Calculated Table 
Dim_Date =
ADDCOLUMNS (
    CALENDAR ( DATE ( 2022, 1, 1 ), DATE ( 2024, 12, 31 ) ),
    "DateKey", INT ( FORMAT ( [Date], "YYYYMMDD" ) ),
    "Year", YEAR ( [Date] ),
    "Quarter", QUARTER ( [Date] ),
    "QuarterLabel", "Q" & QUARTER ( [Date] ) & " " & YEAR ( [Date] ),
    "MonthNumber", MONTH ( [Date] ),
    "MonthName", FORMAT ( [Date], "MMMM" ),
    "MonthShort", FORMAT ( [Date], "MMM" ),
    "YearMonth", FORMAT ( [Date], "YYYY-MM" ),
    "IsMonthEnd", [Date] = EOMONTH ( [Date], 0 )
)

After creating it: select Dim_Date in the Fields pane → Table tools → Mark as Date Table → choose the Date column. Every DATEADD and DATESINPERIOD formula below depends on this one step.

2. Core Business Measures

These are the building blocks — every other formula in this guide reuses one or more of these directly.

DAX — Core Measures 
Total Revenue =
CALCULATE ( SUM ( Fact_Transactions[Amount] ), Dim_RevenueExpenses[REVENUE/EXPENSES] = "REVENUE" )

Total Expenses =
CALCULATE ( SUM ( Fact_Transactions[Amount] ), Dim_RevenueExpenses[REVENUE/EXPENSES] = "EXPENSES" )

Net Income = [Total Revenue] - [Total Expenses]

COGS =
CALCULATE ( [Total Expenses], Dim_Account[LEVEL_01] = "Cost of Goods Sold" )

Gross Margin % =
DIVIDE ( [Total Revenue] - [COGS], [Total Revenue] )

Total Budget = SUM ( Fact_Budget[BudgetAmount] )

Total Actual = SUM ( Fact_Transactions[Amount] )

Budget Variance ($) = [Total Actual] - [Total Budget]

Budget Variance (%) =
DIVIDE ( [Budget Variance ($)], [Total Budget] )

MoM Revenue Growth % =
VAR CurrRev = [Total Revenue]
VAR PrevRev = CALCULATE ( [Total Revenue], DATEADD ( Dim_Date[Date], -1, MONTH ) )
RETURN
    DIVIDE ( CurrRev - PrevRev, PrevRev )

Accounts Over Budget =
VAR AccountVariance =
    ADDCOLUMNS (
        VALUES ( Dim_Account[ACCOUNT_NAME] ),
        "AcctVariance", [Total Actual] - [Total Budget]
    )
RETURN
    COUNTROWS ( FILTER ( AccountVariance, [AcctVariance] > 0 ) )
Reading Accounts Over Budget ADDCOLUMNS builds a small virtual table — one row per account — with each account's own variance calculated next to it. FILTER keeps only the rows where that variance is positive (overspent), and COUNTROWS counts how many are left. This is the same "account by account" logic the Budget vs Actual dashboard is built around, just counting instead of listing.

3. Prior-Period Comparisons (the "▲ +4.2% vs prior period" Number)

Every KPI card shows a small delta against the prior period. Each one needs two formulas: a measure that re-evaluates the KPI one month earlier, and a measure that turns the difference into the number actually shown on the card.

-- 1. Total Revenue
Total Revenue (Prior Period) =
CALCULATE ( [Total Revenue], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Total Revenue Δ% =
DIVIDE ( [Total Revenue] - [Total Revenue (Prior Period)], [Total Revenue (Prior Period)] )

-- 2. Total Expenses
Total Expenses (Prior Period) =
CALCULATE ( [Total Expenses], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Total Expenses Δ% =
DIVIDE ( [Total Expenses] - [Total Expenses (Prior Period)], [Total Expenses (Prior Period)] )

-- 3. Net Income
Net Income (Prior Period) =
CALCULATE ( [Net Income], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Net Income Δ% =
DIVIDE ( [Net Income] - [Net Income (Prior Period)], ABS ( [Net Income (Prior Period)] ) )

-- 4. Gross Margin % (a percentage-point difference, not a percent change)
Gross Margin % (Prior Period) =
CALCULATE ( [Gross Margin %], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Gross Margin % Δ (pts) = [Gross Margin %] - [Gross Margin % (Prior Period)]

-- 5. MoM Revenue Growth %
MoM Revenue Growth % (Prior Period) =
CALCULATE ( [MoM Revenue Growth %], DATEADD ( Dim_Date[Date], -1, MONTH ) )

MoM Revenue Growth % Δ (pts) =
[MoM Revenue Growth %] - [MoM Revenue Growth % (Prior Period)]

-- 6. Total Budget
Total Budget (Prior Period) =
CALCULATE ( [Total Budget], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Total Budget Δ% =
DIVIDE ( [Total Budget] - [Total Budget (Prior Period)], [Total Budget (Prior Period)] )

-- 7. Total Actual
Total Actual (Prior Period) =
CALCULATE ( [Total Actual], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Total Actual Δ% =
DIVIDE ( [Total Actual] - [Total Actual (Prior Period)], [Total Actual (Prior Period)] )

-- 8. Budget Variance ($)
Budget Variance ($) (Prior Period) =
CALCULATE ( [Budget Variance ($)], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Budget Variance ($) Δ% =
DIVIDE (
    [Budget Variance ($)] - [Budget Variance ($) (Prior Period)],
    ABS ( [Budget Variance ($) (Prior Period)] )
)

-- 9. Budget Variance (%) (a percentage-point difference)
Budget Variance (%) (Prior Period) =
CALCULATE ( [Budget Variance (%)], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Budget Variance (%) Δ (pts) =
[Budget Variance (%)] - [Budget Variance (%) (Prior Period)]

-- 10. Accounts Over Budget (a plain count difference, not a percent)
Accounts Over Budget (Prior Period) =
CALCULATE ( [Accounts Over Budget], DATEADD ( Dim_Date[Date], -1, MONTH ) )

Accounts Over Budget Δ =
[Accounts Over Budget] - [Accounts Over Budget (Prior Period)]
Why ABS() Shows Up Twice Net Income Δ% and Budget Variance ($) Δ% both divide by ABS() of the prior-period value. Net Income and Budget Variance can both legitimately cross zero or go negative — dividing by a negative number flips the sign of the percentage and makes the delta arrow point the wrong way on the card. Wrapping the denominator in ABS() keeps the direction of the percentage change reading correctly no matter which side of zero the prior period landed on.

4. Sparkline Measures (the Trend Line on Every KPI Card)

The small trend line under each KPI number needs a measure that's filtered to a trailing window — otherwise it plots every month back to January 2022, which is far too much detail for a sparkline to show usefully. The pattern is the same for every KPI: wrap the base measure in DATESINPERIOD looking back 6 months from whatever the latest date in context is.

DAX — The Sparkline Pattern 
<Measure> (Sparkline 6M) =
CALCULATE (
    [<Measure>],
    DATESINPERIOD ( Dim_Date[Date], MAX ( Dim_Date[Date] ), -6, MONTH )
)

Applied to every KPI, that pattern produces:

Net Income (Sparkline 6M) =

Gross Margin % (Sparkline 6M) =

MoM Revenue Growth % (Sparkline 6M) =

Total Budget (Sparkline 6M) =

5. Putting a Sparkline Measure on the Card

  1. Add a Matrix or Table visual anywhere off to the side of the canvas (it won't be visible in the final layout — it's just where the sparkline gets configured).
  2. Put Dim_Date[MonthShort] on Rows, and the sparkline measure — e.g. [Total Revenue (Sparkline 6M)] — in Values.
  3. Right-click the value field header → Add Sparkline. Power BI asks which date field to plot along the sparkline's X-axis — choose Dim_Date[MonthShort], the same field used across every trend chart in this build.
  4. Drag the finished sparkline onto the KPI card in the position shown in the wireframe (bottom edge of the card, beneath the number and delta).
Why a Separate "Sparkline" Measure at All? You could technically point the sparkline straight at the base measure ([Total Revenue]) — but without the DATESINPERIOD filter, it plots the entire three-year history every time, which is unreadable at sparkline size and re-scales oddly whenever a slicer changes the visible range. The (Sparkline 6M) versions keep every card's trend line showing the same fixed, readable window regardless of what else is filtered on the page.

6. No Extra Measures Needed for the Donuts

It's tempting to assume a donut chart needs its own "percent of whole" measure — it doesn't. Every donut in this build (Revenue Mix, Expense Mix, and the two variance donuts on Dashboard 2) plots a base measure straight from Part 2 directly against a category column. Power BI's donut visual computes each slice's share of the total automatically, at render time, from whatever's in view:

DonutCategory (Legend)Value
Revenue MixDim_Account[LEVEL_02][Total Revenue]
Expense MixDim_Account[LEVEL_02][Total Expenses]
Budget Variance (%) by DepartmentDim_Class[Short_CLASS][Budget Variance (%)]
Budget Variance ($) by AccountDim_Account[ACCOUNT_NAME][Budget Variance ($)]
One Fewer Formula to Maintain A dedicated Revenue Mix % measure (dividing by CALCULATE ( [Total Revenue], ALL ( Dim_Account ) )) is a perfectly valid way to build this if you want the percentage available for a tooltip or a card elsewhere — but it isn't required just to make the donut itself work. The simplest version of any chart is the one built directly from the base measures already in Part 2; only reach for an extra measure when something the chart needs isn't already sitting in the model.

7. The Budget-to-Actual Bridge (Waterfall Chart)

Power BI's native Waterfall visual needs only two fields once the measures above exist — it does the bridge math itself:

  • Category: Dim_Account[LEVEL_01] — the P&L category each step of the bridge represents
  • Breakdown value: [Budget Variance ($)] — the visual automatically walks from the first category's variance to the last, rendering increases as one color and decreases as another

No separate "starting" or "ending" measure is required — set [Total Budget] as the visual's starting value if you want the first bar anchored explicitly, otherwise the waterfall visual infers it from the sum of the breakdown values.

8. The Variance Bars (Account & Department)

Same principle as the donuts — no extra formula needed. Both bar charts on Dashboard 2 plot [Budget Variance ($)] straight against a category column:

ChartCategoryValue
Variance by AccountDim_Account[ACCOUNT_NAME][Budget Variance ($)]
Variance by DepartmentDim_Class[Short_CLASS][Budget Variance ($)]

If you later want a ranked "top 5 over-budget accounts" view, that's the one place a small extra measure earns its keep — a RANKX ( ALL ( Dim_Account[ACCOUNT_NAME] ), [Budget Variance ($)], , DESC ) measure, filtered to ≤ 5 at the visual level. It isn't part of this build, but it's a one-line addition if the need comes up later.

KPI Design

Giving KPIs More Context

A bare number on a dashboard is rarely enough on its own — every KPI card here adds two more things, both powered by the measures above.

"Total Revenue: $1.9M" tells you almost nothing by itself. Is that good? Better than last month? On track? Every KPI card in both dashboards answers that follow-up question before anyone has to ask it:

1. A Comparison, Not Just a Number

Powered by the Δ% (or Δ (pts), or Δ) measure from Part 3 of the DAX Reference — a small colored triangle plus a percentage, ▲ +4.2% vs prior period, sitting right under the headline figure. Green/up means favorable, red/down means worth a second look.

2. A Sparkline

Powered by the (Sparkline 6M) measure from Part 4 — a tiny trend line across the bottom of the card, showing the last six months at a glance. Answers "what's the shape of the recent trend," which the delta number alone can't show.

Both additions cost almost no extra space on the card, and both change what a reader takes away from a two-second glance — which is the whole test for whether a KPI enhancement is worth including at all.

Dashboard 2

Budget vs Actual Analysis

Are we on plan — and where exactly did we drift.

First, the Vocabulary

This dashboard leans on a few terms that are worth defining plainly before looking at a single chart:

Budget

What was planned to be spent or earned, decided in advance — comes from the Fact_Budget table, measured with [Total Budget].

Actual

What really happened — comes from the Fact_Transactions table, measured with [Total Actual], summed to the same level as the budget so the two line up.

Variance

Actual minus Budget — the [Budget Variance ($)] measure. Positive means over plan, negative means under. The whole dashboard is built around slicing that one subtraction different ways.

"Account by Account" Variance

Instead of one lump variance for the whole company, [Budget Variance ($)] gets evaluated separately for each account in Dim_Account. "We're $8,000 over" tells you nothing actionable. "Advertising is $12,000 over, Travel is $4,000 under" tells you exactly where to look first.

Reading the Waterfall (Budget-to-Actual Bridge)

The waterfall chart is the one new chart type here, built entirely from Dim_Account[LEVEL_01] and [Budget Variance ($)] (see Part 7 of the DAX Reference). Read it left to right:

  1. First bar (navy, full height): Total Budget — the starting point.
  2. Middle bars (floating, not touching the bottom): each one is a category's variance. A bar that steps up (green) means that category came in over budget, adding to the total. A bar that steps down (red) means that category came in under budget, subtracting from the total.
  3. Last bar (navy, full height): Total Actual — where you actually landed, after every category's variance has been added or subtracted from the Budget.

The whole chart is a visual "bridge" walking from the plan to the outcome, one category at a time — a much faster read than a table of numbers for spotting which category did the most damage (or the most good).

Why Two Chart Types for the Same Two Breakdowns Account and Department variance each get both a donut and a bar on this page. That's not redundant — they answer subtly different questions. The donut shows share: which account or department makes up the biggest slice of the total variance pool. The bar shows magnitude, ranked and easy to compare side by side. Reading both together catches something a single chart type can miss: an account can dominate the "share of variance" donut while still being a small dollar amount if every other account's variance happens to be even smaller — the bar chart is what confirms whether that share is actually a big number or just a big fish in a small pond.
Layout & Color

The New Wireframe

Canvas 1920 × 1080 (20" × 11.25" — the exact pixel equivalent at 96 dpi), built in PowerPoint, with a classic app-shell layout.

What Changed From a Plain Grid

  • No sidebar. Every slicer now sits in one horizontal strip, positioned between the KPI row and the chart grid — a deliberate hand-off point: filter first, glance at the headline numbers, then read the charts below, all in one downward scan instead of splitting attention between a side panel and the main canvas.
  • Page navigation tabs sit top-right of the header — "Overview" and "Budget vs Actual" — so switching between the two dashboards is a single click, and the active page is always visually obvious. In the wireframe mockup the active tab fills amber gold; in the finished report, Power BI's native Page Navigator visual renders the selected tab in a vivid orange (#EC580D) instead — a small, natural deviation between a hand-built mockup and what the native visual's own styling options actually offer.
  • KPI cards stay lean — icon, label, number, and a delta indicator, with the sparkline dropped entirely. That reclaims real vertical space, which goes straight into the chart grid below.
  • The chart grid is a mirrored two-panel layout, not a single stack. Each panel holds three charts: two compact ones stacked or paired on one side, and one wide "hero" chart — the trend line, the scatter plot, or the waterfall — getting the full width of its panel. Donuts and bars fill the compact slots; anything that needs room to show its shape (a point cloud, a bridge of bars) gets the wide slot instead.

How the Wireframe Was Actually Used

The wireframe didn't stay a mockup — it became part of the real Power BI file. Two versions exist:

  1. The labeled version (pill tags, titles, footer) is the planning artifact — useful for reviewing the layout before building a single visual.
  2. A stripped version — same boxes and KPI icons, but every pill tag, chart title, and footer removed — became the actual page background inside Power BI, set to roughly 13% opacity behind the real visuals. The snapshots below are this second version, pulled directly from the finished .pbix file.
Why Strip the Text for the Real Background Once a real Power BI visual sits on top of a wireframe box, that visual already renders its own title and legend — a leftover "LINE" pill or a placeholder chart title underneath would just be visual noise competing with the real thing. Keeping only the empty box outlines, the KPI icon circles, and the slicer color dots gives just enough of a faint alignment guide to snap real visuals into place, without any text fighting for attention once the real charts are in.
